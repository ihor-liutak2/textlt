Designed for Simplicity. Engineered for Extensibility.

Explore the technical architecture behind TextLT.

TextLT brings document editing, personal notes, and reusable text tools into a native C++ terminal application. Its architecture keeps document state, interface behavior, and integrations in components with distinct responsibilities. Local storage and user configuration support the core workflow, with optional connections for work that reaches beyond the local machine.

A Modular Architecture

Documents, Notes, and Actions are three workspace modes. TextltApp composes their components, the menu and sidebar, and the dialogs. It connects the components through commands and callbacks and supplies shared facilities such as clipboard access and the active theme.

Application composition · Command registration

Native Software. Terminal-Native Experience.

The entry point collects command-line paths, prepares startup resources, and constructs the app. The --startup-check path checks runtime prerequisites and initializes the workspace without entering the interactive loop. In normal use, TextltApp::Run starts FTXUI’s fullscreen loop and saves Notes and Actions when it exits.

FTXUI’s screen, DOM, and component libraries handle the terminal display, element layout, and interactive controls. TextLT renders editor rows and syntax styles, with menus, mouse interaction, dialogs, and keyboard navigation in the same terminal session. Editing helpers work with UTF-8 text and account for character boundaries and display width. The terminal is the application’s primary UI, including when the program runs inside WSL.

Entry point · Editor rendering

Documents as Independent Software Objects

A DocumentSession holds a TextBuffer, undo and redo history, and file state such as path, type, line ending, dirty status, and read-only status. A session can exist in memory before it has a file. DocumentWorkspace tracks open sessions and binds them to panes. Each pane’s EditorViewport holds scroll, cursor, and selection state, and the bound session uses that cursor state during editing.

The layout controller selects the visible arrangement and works with the workspace to assign sessions. Syntax highlighting tokenizes text for display, and the clipboard controller bridges editor operations with terminal paste and platform clipboard facilities. Document conversion extracts text for insertion into the editor.

A Coordinated Editing Environment

Input routing is shared. AppEventDispatcher checks the active UI layer and workspace, handles application shortcuts and focus, and lets FTXUI route ordinary main-screen mouse input through its component tree. Components such as the sidebar, editor, and dialogs still handle their own events. The command registry connects menu commands with the application operations they invoke.

Event dispatcher · Layout controller · Application view

Projects as Organizational Contexts

A project record has an ID, a name, a local folder, and an optional remote connection ID. ProjectStore persists records and the active project ID in projects.json. Registering an existing folder adds or reuses its record. Activating it changes the sidebar root and Git working directory and updates the Notes and Actions project contexts. The open-document list belongs to the shared workspace.

The project menu can assign, change, or unlink a connection. Opening the project’s remote files resolves the saved connection and opens the remote file dialog. New projects can relink a matching Notes group and merge matching Actions groups, so existing material can follow the project context.

Project records · Project activation and connection assignment

Organized Textual Information

A NoteDocument is a structured record containing blocks such as headings, paragraphs, and list items. NoteSession supports editing those blocks. NoteRepository and its serializer maintain local .tlnote files and sections.json, including the project association for a section. The Notes workspace manages search, Markdown import, editing, and Trash restoration. Editor column preferences and note command shortcuts use the app’s settings.

Project activation updates the Notes context inside the app. Note records carry revision and device metadata for local persistence. Cross-device synchronization is outside the current Notes workflow.

Note model · Note persistence · Notes workspace

Extensible Text Processing

The Actions workspace stores groups, pages, cards, and labeled text blocks in actions.json. An Actions group can reference a project, and copying a card block sends its text through the shared clipboard. Text Processors are a separate tool that transforms document content or produces analysis reports.

A bundled registry seeds the user’s processor definitions. A Lua processor supplies transform(text, params) and returns text. The runtime limits execution and exposes selected Lua libraries. The Custom Processor Builder validates and saves user definitions and scripts, allowing more transformations to be added without rebuilding the editor.

Configurable by Design

Settings, project records, connection definitions, and registries have separate loaders. They let users change preferences and choose supported operations without recompiling. The component structure and available external backends are defined in C++.

Application settings · Shortcut persistence · Remote connection store · Bundled processor registry

Adapting to the User’s Terminal

FTXUI decodes character and special-key events. TextLT patches its FTXUI build to distinguish Ctrl+H from Backspace, recognize Alt with UTF-8 input, and support bracketed paste. Shortcut matching accepts several terminal encodings for modified navigation keys and recognizes Ukrainian keyboard equivalents for supported letter shortcuts. On Unix, a terminal guard temporarily adjusts flow control and signal handling and requests distinct modified-key reporting from compatible terminals.

Menu and text actions register defaults in separate shortcut contexts. The registry matches incoming events against effective bindings, and the command registry or editor keymap runs the selected operation. The Keyboard Shortcuts dialog rejects collisions and combinations the terminal may reserve or collapse, and persists accepted changes in shortcuts.json. Users can restore defaults without rebuilding.

Shortcut matching · Layout equivalents · Terminal settings guard

A Customizable Visual Environment

A Theme holds colors consumed by the editor, syntax renderer, menus, dialogs, and other interface components. The loader checks the user directory before packaged locations. It uses the first directory with usable theme JSON files and falls back to a compiled palette. The picker previews themes, while the config stores the selected name and per-theme color overrides. Syntax tokenization and editing behavior remain separate from the choice of palette.

Interoperability Without Unnecessary Complexity

Files and import. C++ filesystem and stream operations back local browsing and persistence. TextImporter uses LibArchive for containers and pugixml for XML. Supported imports such as DOCX, ODT, and FB2 yield text for the editor. RTF has its own conversion path.

Remote files. A provider interface separates file navigation and transfers from the connection backend. SFTP uses OpenSSH’s ssh and sftp executables, FTPS uses external curl for FTP over TLS, and Dropbox uses its HTTP API through RemoteHttpClient and curl. Opening a remote file gives the editor a local cached copy. The Remote Files dialog explicitly uploads the saved copy with Sync Last.

Git and subprocesses. GitManager runs the installed Git executable in the configured working directory and interprets its output for status, diffs, and repository commands. The remote command runner uses Windows process APIs or Unix process creation and pipes, including support for streaming output. Clipboard integration also varies by environment, with native Windows clipboard support and helpers for environments such as Wayland and WSL.

Document import · Remote providers · Process runner · Git integration

Specialized Text Services

Rephrasing and translation. Quick AI takes a selection or paragraph from Docs or an open note. The modal builds a request from a rephrasing mode and optional source and target language instructions. AiBackend streams results from a configured local Ollama server or external provider. HTTP providers use the curl-backed client, while ChatGPT integration runs the Codex CLI app-server and exchanges JSON messages. Profiles store provider and model choices locally, and the settings dialog asks providers for their model catalog. Users can review, copy, or apply the returned text.

Speech. The TTS pipeline prepares document chunks and caches generated WAV audio. The Piper voice registry lists downloadable voice assets. PiperManager resolves installed models and asks the separate, loopback textlt-piper-server to synthesize audio. That CivetWeb helper manages a persistent Piper child on supported Unix builds. The Windows build of the helper lacks that child backend. Playback uses an available system player and has separate playback controls.

Quick AI request and result handling · Provider execution · Piper manager · Speech helper

Local-First by Design

The editor runs locally and can open, edit, and save local files without a service account. Notes, Actions, preferences, and processor definitions are stored locally, and built-in and Lua processors run in the application process. Plain text and Markdown remain portable between tools. Configured remote connections, external model requests, and voice downloads use the network when invoked.

Built on Established Technologies

C++17, C, and CMake
The application is built in C++17. C dependencies include the embedded Lua runtime and the HTTP helper’s server library. CMake builds and installs the targets.
FTXUI 7.0.3
Screen, DOM, and Component provide rendering, layout, the event loop, and interactive controls.
Lua 5.5.1 and nlohmann/json
Embedded Lua executes custom processors. The vendored JSON library reads and writes settings, registries, and structured records.
LibArchive and pugixml
Read archive entries and XML content for document imports.
curl, OpenSSH, Git, Piper, and CivetWeb
Runtime executables handle network, version-control, and speech integrations. CivetWeb serves the separate local Piper helper.
CTest and Python
CTest runs the repository’s C++ test executables and CMake checks, with an optional Python terminal test on Unix.

Release CI packages Linux x64, Windows x64, and macOS arm64 builds. Linux also has an AppImage, and the project documents WSL usage.

Designed for Sustainable Evolution

The source separates document state and file lifecycle, Notes and Actions persistence, remote providers, and modal UI code. Shared helpers cover rendering controls, command registration, JSON storage, and subprocess execution. CMake pins or vendors selected dependencies, and the release workflow builds and runs CTest before packaging. Tests exercise document navigation, Notes and Actions persistence, shortcut handling, import, and remote providers.

Technical references cover FTXUI layout and UI refactoring, and the remote module documents its runtime and transfer behavior. Future changes can build on these component boundaries and test targets.

Architectural Principles

Separation of responsibilities
A document session holds text and history, while a viewport holds pane-local state.
Native execution
The C++ application runs directly in the user’s terminal.
Modular functionality
Documents, Notes, and Actions have distinct data and interaction models.
User control
Users choose settings, configure connections, and explicitly upload remote edits.
Local-first operation
Core editing and local text processing use local files and runtime components.
Configuration and customization
Settings, key bindings, themes, and processor parameters can change at runtime.
Interoperability
Plain text, format import, and established external tools connect workflows.
Extensibility
Parameterized Lua processors add transformations through a defined entry point.
Maintainability
Component-specific tests exercise behavior at boundaries such as storage and input.
Resource awareness
Speech caches audio chunks, and the Lua engine sets execution limits.
